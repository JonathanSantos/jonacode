jonacode · editor de código para a web

Um editor que cabe em qualquer página.

Jonacode é um editor de código pequeno, modular e rápido: destaque de sintaxe, lista virtualizada para arquivos enormes, tema One Dark por padrão e uma API simples para criar linguagens (até inventadas). Funciona em HTML puro, React, Vue, Angular ou onde houver um <div>.

visão geral · comparativo

Leve e rápido: o espaço que faltava.

Os editores pequenos travam com arquivos grandes, e os que aguentam arquivos grandes são pesados. O Jonacode foi feito para ficar no meio: pequeno, virtualizado, fácil de integrar e de estender. Aqui ele aparece lado a lado com CodeMirror 6, CodeMirror 5, Monaco, Ace, prism-code-editor e CodeJar. Os números foram medidos na mesma máquina, com configurações equivalentes, e as notas trazem pesos que você pode ajustar.

O mapa

Cada ponto é um editor com destaque de JavaScript e o seu "setup básico". No eixo horizontal, o tamanho do JavaScript (gzip); no vertical, o tempo até a primeira pintura de um arquivo de 100 mil linhas. Os dois eixos estão em escala logarítmica, e quanto mais perto do canto inferior esquerdo, melhor.

Medido, não estimado

Em todos os gráficos, menos é melhor. Os tempos incluem a espera do próximo quadro (~16 ms), então diferenças abaixo disso são ruído. As variantes "núcleo" mostram o custo mínimo de cada biblioteca, sem linguagem nem extensões.

Reproduza na sua máquina: cd bench/compare && npm install && npm run bench, depois npm run docs. A memória JS (V8) está só na tabela porque não inclui o DOM: editores que criam centenas de milhares de nós aparecem artificialmente "leves" nela.

Recursos

✓ pronto no pacote · ~ parcial, via addon/comunidade ou com ressalvas · ✗ ausente.

Notas e pesos ajustável

Cada critério recebe uma nota de 0 a 10. Tamanho e desempenho vêm das medições; os demais são avaliação nossa, e estão abertos na tabela logo abaixo. O peso de cada critério depende do seu projeto: escolha um perfil ou mexa nos controles e veja o ranking se reorganizar.

Onde ainda perdemos

O núcleo técnico já compete com os grandes; o que falta é maturidade. Nas últimas rodadas entraram 11 linguagens prontas (com aninhamento), o editor que cresce com a página, o leitor de tela, a validação no Android, o destaque estático que vira editor sob demanda, o visualizador de logs, mais de 1 milhão de linhas, o campo de formulário nativo, os importadores de temas do VS Code e de gramáticas do Monaco, o laboratório com testes de gramática, marcações, tooltips, diagnósticos, autocomplete, folding e busca em várias linhas, o capítulo de IA (ferramentas para agentes, edições no formato da IA, diff com revisão, texto fantasma e Ctrl/⌘+K), a validação com tree-sitter (árvore sintática e seleção por estrutura), a edição colaborativa com Yjs, as zonas entre linhas, o suporte a qualquer fonte e mais de 400 testes de interface em Chromium, Firefox e WebKit, que já acharam e corrigiram 15 bugs. Estas são as lacunas que sobram, na ordem em que pretendemos atacá-las:

  1. Confiabilidade. Validação no iOS; teste com NVDA, VoiceOver e TalkBack; CI rodando no GitHub e publicação no npm.
  2. Linguagem de verdade. Integração com LSP (em um worker) para autocomplete, diagnósticos e tooltips com tipos; folding pela árvore do tree-sitter.
  3. Escrita. Texto da direita para a esquerda (RTL e bidirecional).

Instalação

Primeiro editor

O editor ocupa a altura do elemento pai. Dê uma altura ao container (e o editor passa a rolar e a virtualizar) ou deixe sem altura para ele crescer com o conteúdo.

Só destacar, sem editor SSR

Para blocos de código que ninguém vai editar (um blog, uma página de documentação), você não precisa do editor. highlight() usa as mesmas gramáticas e temas e devolve uma string de HTML, sem tocar no DOM: roda no servidor, num gerador de site estático ou no navegador.

Só o destacador, com JavaScript e o One Dark, pesa ~6 kB gzip, sem nada do editor.

Editor sob demanda ao vivo

Uma página com muitos trechos editáveis não precisa pagar por todos os editores de uma vez. lazyEditor() mostra o destaque estático e só cria o editor no primeiro clique, toque ou foco (ou quando o bloco entra na tela, ou quando o navegador fica ocioso). O bloco estático tem a mesma geometria do editor: margens, altura de linha e números de linha. A troca acontece sem nada se mexer, e o cursor cai onde você clicou.

capítulo 3 · frameworks

Um núcleo, vários sabores.

O núcleo é DOM puro. Os adaptadores são arquivos pequenos e separados: você só paga pelo que importar.

Adaptadores

O <jona-code> funciona em qualquer lugar que renderize HTML. Nada é registrado até você chamar defineJonacodeElement(), e o conteúdo inicial vem do próprio elemento.

Ao vivo, logo abaixo, um <jona-code> de verdade:

// Eu sou um <jona-code> — edite à vontade const frameworks = ['React', 'Vue', 'Angular', 'Svelte'] frameworks.forEach((nome) => console.log(`${nome} ✓`))

Atributos: language, theme, readonly, line-wrapping, placeholder, tab-size, font-size, min-lines, max-lines, name, required e lazy. Propriedades: value, editor, language, theme, extensions.

Controlado (value) ou não controlado (defaultValue). O ref aponta para a instância do Editor.

Em formulários ao vivo

O <jona-code> é um elemento associado a formulário, como um <textarea>. Com um name, ele vai junto no envio; form.reset() volta ao conteúdo inicial; required participa da validação; um <fieldset disabled> o deixa só leitura (e fora do envio); e um <label for> dá nome a ele e o foca. Tente enviar vazio:

SELECT id, nome FROM clientes WHERE ativo = true

Também há validity, checkValidity(), reportValidity() e setCustomValidity(), como em qualquer campo. Em documentos enormes o valor do formulário é atualizado com atraso de 300 ms, para não montar o texto inteiro a cada tecla.

Ciclo de vida

  • Criar: createEditor(elemento, opções) monta o DOM do editor dentro do elemento.
  • Atualizar: editor.setOptions() troca linguagem, tema, extensões, readOnly e fonte sem recriar nada.
  • Destruir: editor.destroy() remove o DOM, observers e listeners. Os adaptadores fazem isso por você.
  • Shadow DOM: os estilos são injetados no document ou na ShadowRoot onde o editor estiver.

capítulo 5 · linguagens

Estados, regex e nada mais.

Uma linguagem é uma máquina de estados declarativa. Cada estado tem uma lista ordenada de regras: uma regex e o token que ela produz. Regras podem empilhar, desempilhar ou trocar de estado, e é assim que comentários de várias linhas e template strings aninhadas funcionam.

Gramáticas do Monaco

O Monaco (o editor do VS Code na web) traz ~80 gramáticas no formato Monarch, muito parecido com o do Jonacode. fromMonarch() lê o objeto language de uma delas e devolve uma linguagem do Jonacode, com os nomes de token convertidos para os dos nossos temas (identifier → variable, delimiter → punctuation…). Ele entende atributos (@keywords), cases, @push/@pop/@popall, subestados com $S2, @rematch, grupos e linguagens embutidas (nextEmbedded).

Testando gramáticas

Gramáticas quebram de jeitos sutis, então vale testá-las. jonacode/testing usa um formato fácil de ler: a linha de código e, embaixo, ^ sob cada token com o tipo esperado. Funciona com node:test, Vitest, Jest ou qualquer outro, porque só lança um erro. describeTokens() gera esse texto a partir de um exemplo, para você revisar e colar.

Quando um token não confere, o erro mostra a linha, o esperado e o encontrado, e o bloco certo para copiar e colar no teste.

Tokens personalizados ao vivo

Precisa de um tipo de token novo, como todo, url, cor ou sql? Há três caminhos, do mais simples ao mais poderoso, e todos terminam em uma classe CSS que você estiliza como quiser.

1. Capture sem mexer na gramática

tokenRule roda uma regex sobre a linha já tokenizada e dá um tipo novo ao trecho, opcionalmente só dentro de um tipo (comment, string…).

2. Estilize como quiser

tokenStyles aceita qualquer propriedade CSS e vale só para este editor, por cima do tema. Também funciona no tema (tokens) ou em CSS puro (.jc-t-todo).

3. Na própria gramática: qualquer regra pode emitir qualquer nome, e extendLanguage(javascript, { prepend: { root: [...] } }) adiciona regras a uma linguagem existente sem reescrevê-la. Use-o quando o token novo muda o estado (ex.: SQL dentro de sql`…`); para marcar trechos dentro de tokens que já existem, prefira o tokenRule.

Edite as regras à esquerda. O editor da direita tem o tokenInspector() ligado: passe o mouse sobre qualquer token para ver o tipo e a classe que você pode estilizar.

tokens.js
resultado · passe o mouse

Evite no estilo propriedades que mudam a largura do texto (padding, margin, letter-spacing, font-size): o editor mede a fonte uma vez para todo o texto, então um token mais largo que os outros desalinha o cursor dali em diante. Fundos, box-shadow, outline, cores, sublinhados, itálico e negrito são seguros. Um token pode ter até CSS próprio: style: (m) => `--swatch:${m[0]}`.

capítulo 6 · por dentro

Como ele funciona por baixo dos panos.

Como o Jonacode fica rápido e pequeno: do caminho de uma tecla até a virtualização, a tokenização, a geometria e as fontes. Quase toda seção abaixo tem uma demonstração rodando o código de verdade.

O caminho de uma tecla

Todo o estado passa por um único ponto, editor.dispatch(transação). Uma transação descreve mudanças no texto e a nova seleção. O documento, o highlighter e o histórico são atualizados, e o render é agendado para o próximo frame (ou executado na hora quando a mudança vem do usuário).

Lista virtualizada ao vivo

A altura total é linhas × alturaDaLinha, então a barra de rolagem é real. Mas só as linhas da janela visível (mais uma margem, o overscan) existem no DOM. Cada elemento de linha tem uma chave estado + texto: ao rolar ou editar, elementos com a mesma chave são reaproveitados e só o que mudou é reconstruído.

Quebra de linha ao vivo

Com lineWrapping: true, o Jonacode calcula as quebras em JavaScript em vez de deixar o navegador quebrar. Cada linha guarda os pontos onde as linhas visuais começam (depois de espaços quando possível, no meio da palavra quando não) e um <br> é inserido ali. Como as posições são conhecidas sem medir nada, a virtualização continua exata.

Linhas passam a ter alturas diferentes, então um mapa de alturas guarda a altura de cada linha em px (as linhas visuais, mais o espaço de zonas e blocos; zero quando está dobrada), com somas prefixadas calculadas sob demanda: "onde começa a linha N" é O(1) e "qual linha está no pixel Y" é uma busca binária. Mude a largura e veja o mapa se refazer:

Cresce com a página ao vivo

Sem altura definida no elemento pai, o editor cresce com o conteúdo e a rolagem passa a ser a da página. A virtualização continua: em vez da área do próprio editor, o Jonacode desenha a interseção do editor com a janela e com cada ancestral que rola, e redesenha quando qualquer coisa em volta rola.

  • minLines dá uma altura mínima (bom para campos vazios) e maxLines limita o crescimento: dali em diante o editor rola por dentro.
  • Quando o cursor sai da tela (Page Down, busca, scrollIntoView), quem rola é a página.
  • No <jona-code> são os atributos min-lines e max-lines; no React e no Vue, as props minLines e maxLines.

Milhões de linhas ao vivo

Os navegadores limitam a altura de um elemento (o Firefox a ~17,9 milhões de px, os outros a ~33,5 milhões): com 22 px por linha, isso acaba perto de 800 mil linhas. Acima de 10 milhões de px o Jonacode entra em modo compacto: a área rolável fica com 10 milhões de px, a barra de rolagem mapeia proporcionalmente para o documento inteiro e as linhas desenhadas ganham um deslocamento para cair no lugar certo. A roda do mouse, Page Up/Down e o arraste continuam movendo o texto 1:1.

Tokenização incremental ao vivo

O highlighter guarda o estado no início de cada linha. Uma edição invalida a partir da linha editada, mas a re-tokenização para assim que o estado recalculado bate com o antigo: a partir dali, nada mudou. Os estados são internados (pilhas iguais são o mesmo objeto), então a comparação é um ===. Além disso o trabalho é preguiçoso e só vai até a última linha visível; o resto é feito em segundo plano, em fatias que usam só o tempo ocioso do navegador (requestIdleCallback), então nunca atrasam um quadro. Num salto para o meio de 100 mil linhas, as linhas aparecem com o melhor estado conhecido e a cor é corrigida logo depois.

Edite o código: as linhas re-tokenizadas piscam e a coluna da esquerda mostra o estado no início de cada linha.

Pintura dos tokens medido

Pintar é o caminho mais quente do editor: acontece a cada tecla e a cada frame de rolagem. Estas são as otimizações, das regex até o DOM:

  • Despacho pelo primeiro caractere. Na definição da linguagem, cada regex é analisada estaticamente para descobrir quais caracteres ASCII podem iniciar um casamento. Numa posição, o tokenizador só testa as regras possíveis para aquele caractere. Na gramática JavaScript isso deu 1,8× mais velocidade (303 mil → 549 mil linhas/s em código real), com saída idêntica.
  • Reaproveitamento por chave. Uma linha só é repintada se o texto, o estado inicial ou o layout mudaram, e a comparação é feita campo a campo, sem montar strings.
  • Cache LRU de HTML. O HTML das últimas 2.500 linhas fica guardado: rolar para cima e para baixo não re-tokeniza nada.
  • Um innerHTML por linha, com tokens adjacentes do mesmo tipo já mesclados, e contain: layout style em cada linha, para que mudanças não recalculem o resto da página.
  • Trabalho só na tela. Tokens e transformações (tokenRule) só rodam para as linhas renderizadas.

Geometria

  
Converter coluna ↔ pixel precisa ser barato, porque acontece em cada tecla e em cada clique. Para linhas só com ASCII numa fonte monoespaçada (a grande maioria em código), a conta é aritmética: x = colunaVisual × larguraDoCaractere, com tabs expandidos até a próxima parada. Para linhas com emoji, CJK ou acentos combinados, e para qualquer linha numa fonte proporcional, o editor mede o texto renderizado com um Range do DOM e faz busca binária no clique.

  

  
O movimento do cursor também respeita grafemas: 👍🏽 são 4 unidades UTF-16, mas um passo de cursor.


  
Fontes e tamanhos ao vivo

  
Qualquer fonte e qualquer tamanho funcionam: pela opção (fontFamily, fontSize, lineHeight) ou só pelo CSS (--jc-font-family, --jc-font-size, --jc-line-height, uma classe no pai, o zoom). O editor mede a fonte num elemento escondido ao lado das linhas, que herda os mesmos estilos, e mede de novo sempre que ele muda de tamanho: uma web font que termina de carregar, um tema novo, uma media query.

  
    
    
  • Medida com fração de pixel: a largura do caractere vem de 200 caracteres medidos sem arredondar. Arredondada, ela desviava um pixel a cada poucas centenas de colunas.
    • 
    
  • Fontes proporcionais: o editor percebe quando i e W têm larguras diferentes. Aí mede o texto de verdade para o cursor e os cliques, e quebra as linhas pela largura de cada caractere.
    • 
    
  • Negrito e itálico: quando a fonte não tem negrito, o navegador pode fabricar um mais largo (o Safari faz isso). O editor mede os dois e não deixa o cursor escorregar depois de um token em negrito.
    • 
    
  • Altura da linha em pixels inteiros (como os blocos estáticos, com round()). A largura do gutter dos números usa a largura de um dígito, então os números cabem mesmo em fontes proporcionais.

Zonas e widgets ao vivo

  
Para colocar elementos seus entre as linhas, como uma barra de ações acima de uma função, um texto, um comentário ou uma prévia, use addZone. É o que o Monaco chama de view zone. A zona ocupa espaço próprio, as linhas de baixo descem, e ela não vira parte do texto: o cursor pula por cima, copiar não a leva junto e a numeração continua certa.

  
    
    
  • Altura automática: a zona mede o próprio conteúdo e acompanha quando ele muda (antes da pintura, sem piscar). Também aceita altura fixa em px ou em linhas (lines: 2 cresce junto com a fonte).

  • Acompanha as edições: Enter no começo da linha leva junto a zona de cima; no fim, a zona de baixo fica embaixo da linha. Some quando a linha está dobrada.

    • 
    
  • Interativa: cliques, campos e seleção de texto dentro da zona são dela; o editor não mexe no cursor. Os botões de actions rodam sem tirar o foco do código.

Validação com tree-sitter ao vivo

  
O destaque do Jonacode é um tokenizador rápido, não um parser: ele pinta, mas não sabe se o código é válido. Para isso existe o treeSitter(), que roda o tree-sitter (o parser do GitHub, do Neovim e do Zed, compilado para WebAssembly) ao lado do editor:

  
    
    
  • Validação. Os erros de sintaxe viram diagnósticos: sublinhado ondulado, marcador na margem, tooltip e F8. Convivem com os do seu linter, cada fonte no seu conjunto.
    • 
    
  • Correção. Quando o deslize é claro, o tooltip oferece a correção: inserir o ) que falta, remover a vírgula sobrando no JSON, fechar o [, a string ou o if do bash (fi). O fechamento vai para onde a indentação do bloco termina, não para o fim do arquivo. fixAllSyntax aplica todas num passo de desfazer.
    • 
    
  • Linguagens aninhadas. O código dentro de <script> e <style> no HTML e dos blocos de código no Markdown é validado com a gramática dele.
    • 
    
  • Sem travar. A análise é incremental e roda em tempo ocioso, em fatias de 6 ms: num arquivo de 20 mil linhas, o pior quadro enquanto carrega, analisa e reanalisa ficou em 17–18 ms no Chromium e no Firefox e em até 30 ms no WebKit (um quadro são ~17 ms).
    • 
    
  • Árvore sintática. syntaxTree(editor) e nodeAt(editor, pos) dão a árvore às suas extensões, e Alt+Shift+→/← (⌃⇧⌘+→/← no macOS) expandem e encolhem a seleção por nó.

Um editor que a IA sabe usar.

  
Dois tipos de IA mexem num editor de código: a do seu produto, que você liga a um modelo, e a de fora, um agente de navegador que olha a página e digita como uma pessoa. O Jonacode atende os dois com peças opcionais, sem depender de nenhum provedor: você decide qual modelo chamar e como.


  

    

      A IA do produto
      
Seu app liga um modelo ao editor. O modelo lê, busca, edita e vê os erros por ferramentas prontas; a pessoa revisa cada trecho.

      editorTools() applyEdits() diffView() inlineSuggestion() inlineEdit()
    

    

      A IA de fora
      
Um agente de navegador preenche o campo, lê a árvore de acessibilidade ou chama ferramentas que a página oferece.

      preencher campo aria-description exposeTools()

Agentes de navegador

  
Editores virtualizados costumam ser hostis a agentes que operam a página: só as linhas na tela existem no DOM, e o campo de texto escondido guarda só um pedaço. O Jonacode trata os três caminhos que esses agentes usam:

  
    
    
  • Preencher o campo. Quando um script ou uma ferramenta de automação seleciona o campo inteiro e digita (o “fill” do Playwright, o preencher do agente), isso vale pelo documento inteiro, num passo de desfazer. Se o script só alterou a página que leu do campo, só ela muda.
    • 
    
  • Ler a árvore de acessibilidade. O campo diz que é uma parte do arquivo: aria-description="Lines 21–30 of 200" (traduzível por phrases). Leitores de tela ganham a mesma informação.
    • 
    
  • Chamar ferramentas. exposeTools(editorTools(editor)) registra as ferramentas na proposta WebMCP quando o navegador a oferece; sem ela, não faz nada.

Proteções e verificação ao vivo

  
readOnlyRanges([...]) protege trechos que ninguém edita, nem a pessoa nem a IA: bom para exercícios (“só edite dentro da função”) e modelos de CMS.
